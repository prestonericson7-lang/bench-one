## 2. Corrections — claims of mine the measurements overturned

### A threshold sweep returns a cliff edge by construction

Document 40 published write 5 / read 8 after verifying 8 MB with zero errors. The identical binary,
later the same day, reported about 6,900 wrong bytes in the same 8 MB, stable across five runs.

The sweep that produced those settings asked *what is the fastest setting that passes* and took the
answer. That returns the edge of a cliff and nothing else. The clean window for reads runs from 8 no-ops
to at least 40; 8 shipped.

### The driver was not running the code that had been tested

With the settings corrected it still produced one to three wrong bytes per 8 MB while four soaks covering
264 MB insisted the configuration was clean. Its write loop was hand-unrolled eight bytes at a time and
every qualifying test used a plain loop — so at the same no-op count **the driver wrote 4.4% faster than
the tests**, out past the margin they had measured.

> A no-op count is not a timing specification. It is a timing specification for one exact instruction
> sequence, and changing the surrounding loop changes what it means.

The 4.4% discrepancy was printed in every run from the first and went unread for four hypotheses.

### Four hypotheses, each with the test that killed it

| believed | disproved by |
|---|---|
| an address line, because errors only appeared over 8 MB | `psram_addr_fault` — every word carries its own address, so a wrong word names its own fault. 28 of 18,385 were aliases. Not a wire |
| recovery after a long run of writing | its **own control line** — at the end of the same run, with no wait, the read was clean. The 0 ms row was simply always first |
| going idle | `psram_idle` — 264 MB across cold, warm and primed arms, zero errors in any |
| the test data being quieter than the driver's | `psram_pattern` — ascending addresses, pseudorandom, 0x00/0xFF, 0x55/0xAA. All clean |

### The Teensy had been running the scalar kernel for the life of the figure

`gguf_dot.c` has hand-written AVX2 and NEON paths and a header saying the NEON one exists because every
weight-carrying node here is ARM. **A Teensy 4.1 is a Cortex-M7: no NEON.** So the project's headline
39.3 MB/s was the portable fallback, and the benchmark never printed which path it had measured.

### A benchmark whose result nobody reads measures nothing

The first run of the matrix test reported its on-chip case at **0.000 ms and 275 million MFLOP/s**,
because the loop's result was discarded and the compiler deleted the loop. A timed empty loop divided by
a constant operation count looks exactly like a measurement.

### The textbook GEMM loop was my fault, not the chip's

9.19 cycles per multiply-accumulate on a floating point unit the vertex transform drove at about 1.6.
`c[j] += av * b[j]` loads and stores `c[j]` every iteration. Holding a 4×4 tile in registers: 2.41
cycles, **3.8× faster, zero elements differing.**

### I estimated the wrong bottleneck by a factor of three

I put Q4_K's per-sub-block double arithmetic at 61% of its time. Measured by removing one stage at a
time: **nibble loop 65%, scale unpack 15%, float and double arithmetic 20%.**

### Two verdicts of mine could not have been right

The retention test printed "IT ROTS" on a run whose before-count was already 155 and whose five-second
wait added three. The failure message blamed refresh for what turned out to be a cold-start effect. Both
now say *inconclusive* when they cannot distinguish their own cases.

### And one regression caught before it shipped

Hoisting the activation sums into the runtime would have **dropped x86 and every Cortex-A node off their
vector paths**, because the hoisted kernel only had a Cortex-M7 implementation. The host suite would not
have caught it: it checks correctness, and the scalar answer is correct.

## 3. What a clean test is worth, which is the thread running through all of it

A clean pass over 8 MB bounds the error rate below about one in eight million. The rate being hunted was
two in ten million. **The sweeps were not lying; they had no resolution left at the scale that mattered**,
and not one of them said so.

| | bound on the error rate |
|---|---|
| 8 MB clean | under 120 per billion bytes |
| 264 MB clean | under 3.8 per billion |
| what the driver was actually doing | about 240 per billion |

`psram_soak` now prints the bound instead of a verdict: bytes beside errors, the rate in parts per
billion, and for a configuration that has not failed yet, the bound that stands in for a rate and falls
as the soak runs. **There is no such thing as a measured zero, only a bound that has not been beaten.**

## 5. What is next, in the order it matters

1. **One wire.** Move the decoder enable from pin 48 to pin 5 and the bank goes from 8 MB to 48, with
   nothing desoldered. `psram_bank6` detects which wiring is present and will report 48 MB without being
   edited. Document 44.
2. **The perfboard.** Under 20.2 ns per nibble hands the transfer to the hardware controller: 13.8 → 33
   MB/s, which is 2.4× on the token rate. Confirmed as the only remaining route after `psram_pads`
   showed all eight pad configurations give identical speed.
3. **More nodes.** Per-layer cost is independent, so layers split across boards multiply throughput
   directly. The cheapest axis and the reason the machine is a fleet.
4. **Not the arithmetic.** Already five times faster than the bus feeds it, in the real format.

## 6. Rules earned today

1. Never ship the fastest setting that passes. Find where the clean region ends on **both** sides.
2. Qualify the code that ships, not a copy of it.
3. Never read a fixed-order sweep as causal. Run it in both orders.
4. Vary one thing, then vary the **pair** — two single-variable sweeps can both pass while the
   combination fails, because neither visits it.
5. Quote the bound, not the zero. Print the bytes tested beside every clean result.
6. When two tests of the same thing disagree, diff the code before theorising about the hardware.
7. A benchmark that cannot name the implementation it measured is one rename away from measuring the
   wrong thing, and will not tell you.
8. Measure the good implementation before concluding anything about the hardware.
9. Ask which kernel *this target* will actually run, before shipping rather than after publishing.
