Brain and Radio

A binary framing protocol built from scratch for a direct UART between two microcontrollers — no COBS, no Protobuf, no SLIP. The Teensy is the brain. The ESP32 is a radio. Every decision below follows from that one sentence.

01

The division of labour

The ESP32 is a capable computer, and the temptation to let it think is constant. Resist it. The rule that settles every design argument in this project:

The rule

Mechanism lives on the radio. Policy lives on the brain. The radio knows how to drive an 802.11 MAC — start a scan, attempt a join, read a reason code. It reports what happened. It does not decide what happens next.

Three consequences you can point at in the code:

  • The radio reports raw facts beside its summary. A connect response carries a friendly status byte and the raw 802.11 reason code. Reason 15 and reason 202 both mean “wrong password” to the radio — but 202 is an outright rejection, while 15 is a handshake timeout, which is also what a correct password produces at the edge of range. Only the brain has the context to tell those apart.
  • The radio can speak without being asked. Links drop and chips brown out on the radio’s schedule, never the brain’s.
  • The radio is replaceable. Nothing in the frame format mentions Espressif. Auth modes and status codes are translated to our own enums at the radio’s edge.
02

The frame

Seven fields, five of them fixed. Everything the protocol guarantees is enforced by two of them working together: the length field bounds the frame, and the CRC validates it.

FieldSizeWhy it exists
START1 B A serial link has no packet boundaries. When the receiver loses its place it scans for 0xAA — binary 10101010, rare in structured data and unmistakable on a logic analyser. Not escaped; see §04.
LEN2 B Big-endian count of CMD + payload. One byte would cap a frame at 255 and a scan of 20 networks already exceeds that. Two bytes cost one byte and buy headroom to 65535.
SEQ1 B Ties a response to its request. 0x00 is reserved to mean unsolicited. Without SEQ, one timeout shifts every later response by one — a desync that looks like random nonsense.
CMD1 B Requests and responses use distinct values rather than a shared reply flag, so a hex dump is self-describing.
PAYLOAD0–1018 B Command-specific. May be empty.
CRC81 B A frame that fails its CRC is dropped, never partially acted on. That is the central rule of the protocol.

The CRC, and a naming trap worth knowing about

The specification this was built from asked for “CRC-8/MAXIM (Dallas/iButton)” and for “poly 0x31, init 0x00, no reflect, no XOR out”. Those describe different algorithms, and the difference is invisible until someone else tries to interoperate.

VariantParameterscheck("123456789")
CRC-8/MAXIM-DOW the real one poly 0x31, reflected, init 0x00 0xA1
Implemented here this protocol poly 0x31, MSB-first, init 0x00 0xA2
CRC-8/NRSC-5 poly 0x31, MSB-first, init 0xFF 0xF7

The explicit parameters were followed rather than the label, because parameters are unambiguous and labels are not. Both boards share one implementation, so they interoperate either way — the name only matters the day a Python harness or a logic-analyser decoder has to speak this protocol. On that day, hand them the middle row, not the word “MAXIM”.

The 256-byte lookup table was generated and then checked against an independent bitwise implementation across every one-byte input, all 65,536 two-byte inputs, and 5,000 random strings: 70,793 cases, zero mismatches. It was never typed by hand.

04

The parser

A byte-at-a-time state machine. It never blocks, never allocates, and has a defined answer for every byte in every state — which is the only structure that survives arbitrary garbage on the line.

What happens when 0xAA appears inside a payload

It does, constantly. −86 dBm as a signed RSSI byte is 0xAA, and that is an ordinary signal strength in a block of flats. Two filters reject the impostor, and the arithmetic is worth knowing because it is what justifies not byte-stuffing at all.

A claim this page used to make, which hardware disproved

This section previously said a rejected false start costs “at most one lost frame”. That was wrong. A false sync declaring an enormous length sent the parser into its drain state waiting for bytes that were never coming, swallowing every real frame until the 50 ms timeout — up to ~4,600 bytes at this baud. It ate a live PING during bring-up.

The parser now separates “a real frame, too big for us” from “not a frame at all”. A declared length within 2× the frame size is drained precisely (that is a peer built with a bigger buffer); anything larger is judged a false start and resyncs immediately, because our own builder refuses to emit more than 1019 bytes. The real bound is 2048 bytes, about 22 ms — comfortably inside the inter-byte timeout.

The timeout bug this design had, and how it was fixed

The inter-byte timeout must be evaluated only when the receive queue is empty. Checking it before draining lets a slow reader impersonate a dead sender: bytes that arrived on time and are sitting in the UART buffer get discarded because we were late. It presents as “long responses randomly fail” — and the harder you debug it with print statements, the more reliably it reproduces, because printing is what made the loop slow. Data still queued is proof the peer is alive. Only silence justifies a timeout.

Why error NACKs are rate limited

On a badly broken link — baud mismatch, floating ground, a board rebooting in a loop — both ends see continuous nonsense and both dutifully emit an error frame per malformed frame. Those cross the broken link, arrive corrupted, and provoke more of the same. At 921600 baud that feedback loop saturates the wire in both directions with complaints, and the actual fault is buried under the noise its own reporting created. A persistent error is worth reporting once. Suppressed NACKs are counted and printed, never silently dropped.

7b

What this is, and is not

This architecture is not novel, and saying so plainly is more useful than the alternative. Espressif ship ESP-Hosted-MCU — any host MCU plus an ESP as radio, with a 12-byte binary header carrying both a checksum and a sequence number. Arduino ship nina-fw, which is what Teensy users actually run today. Teensquitto did Teensy + ESP8266 with custom binary framing in 2017. And Klipper — length, sequence, CRC-16, sync byte, running on Teensy, in 3D printing — is on hundreds of thousands of machines.

So the pattern is a product category and the framing is well-trodden. What is honestly distinctive here is narrower: there is no public Teensy binding of the vendor’s own design, and the closest Teensy-specific work uses an XOR checksum with no sequence numbers, no written spec and no tests. Against that baseline, a resynchronising parser, a verified CRC, 1.4 million assertions and a documented failure log are a real step up — better-built than the existing option, not first.

One claim that is specific and checkable

This framing is more robust than Espressif’s own UART transport. ESP-Hosted has no start marker, no byte stuffing and no resync: both ends read a fixed 12 bytes and continue on error from the same misaligned offset, so a single stray byte desynchronises it permanently (their issues #51 and #142). Their fix was to flush the receive FIFO after reset rather than add a sync marker.
