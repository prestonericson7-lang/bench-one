## 2. What the model file turned out to be

Read out of the Ollama blob on this disk, not from documentation:

| | |
|---|---|
| architecture | qwen2, 36 layers, dim 2048, hidden 11008 |
| attention | 16 heads, 2 key-value heads, 128 per head |
| quantization by bytes | 69% Q4_K, 31% Q6_K |
| **per layer** | **49.2 MB** |
| **output head** | **243.4 MB, and TIED to the embedding table** |
| tensors | 434, which is exactly 36 × 12 + token_embd + output_norm |

That last row is the whole finding: **there is no separate output weight.** The embedding table is the
output projection. It changed two decisions and is why half of section 4 exists.

## 3. It runs, and it is correct

```
The capital of France is Paris. Paris is the largest city in France and is known
```

Coherent output is the only test that catches a wrong Q4_K unpack, a wrong rotary pairing and a
mis-mapped key head all at once, because each of those produces fluent nonsense at exactly the right
speed. It passed on the first run.

Then the distributed version was checked against it properly. Four processes, each holding a slice of
the layers and a slice of the vocabulary, none holding the model:

```
Write a function that reverses a linked list in place. The function should take the head of
the linked list as an argument and return the new head of the reversed list.
```

**Byte for byte identical to one process, over 30 tokens.** One test covering layer-range loading,
cost-balanced splitting, the vocabulary-split head, the disk-backed embedding lookup, the two-lap
protocol, per-stream KV caches and batched prefill.

## 4. Every claim of mine the measurements overturned

This is the section that matters. Nine of my own numbers were wrong today.

| claim | what I said | what it is | how it was found |
|---|---|---|---|
| FPGA advantage over the ARM cores | 31× | **~15×** | writing a decent unpack kernel |
| desktop's unpack gap vs memory | 6× | **2.8×** | same |
| a hop between nodes | 29 µs | **148 µs** | measuring two machines instead of one |
| Luckfox unpack rate | 127 MB/s | **61 MB/s** | running it on the board |
| Teensy unpack rate | 58 MB/s | **39.3, and 21.4 from PSRAM** | running it on the board |
| combining memory and unpack limits | take the slower | **they ADD on a CPU** | Teensy, confirmed on the desktop |
| where the embedding table lives | on an SD card | **must be in RAM, then split** | the head is tied |
| how many FPGA lanes to build | 64 | **256** | synthesizing 64 through 1024 |
| fleet usable bandwidth | 53.27 GB/s | **43.82 GB/s** | the two corrections above |

### 4a. The unpack kernel: I was blaming the format for a bad loop

`decode_limit` said 4-bit unpacking ran at 5.2 GB/s against 29.4 GB/s of memory, and docs/23 concluded a
six-fold gap and a 31× case for the FPGAs. That measured an implementation which wrote 256 floats to
memory per 144-byte block so a dot product could read them back once each.

Reassociating the arithmetic — `d*sc * Σ(q·x) − dmin*m * Σx`, two float multiplies per 32 weights
instead of one per weight, integers straight out of the nibbles — gave **4.26× on Q4_K** and took the
real runtime from 1.28 to 4.25 tokens a second with identical output.

Proving it was its own lesson. The first correctness test used a realistic activation, reported 6% mean
error, and could not distinguish a broken kernel from a correct kernel paying the honest cost of 8-bit
activations. Two questions need two tests: an activation chosen so int8 quantization is *exact* gave
**5.89e-08** worst case over 1280 rows of real tensors. That test also found a real defect — a float
accumulator losing 3.5e-04 on an 11008-wide sum that nearly cancels. One double per row fixed it.

### 4b. Lanes are nearly free, so build more of them

Synthesized with yosys against `xc7`:

| lanes | logic cells | % of the XC7Z020 | peak unpack |
|---|---|---|---|
| 64 | 2,611 | 4.9% | 3.2 GB/s |
| 128 | 5,168 | 9.7% | 6.4 GB/s |
| 256 | 10,030 | 18.9% | 12.8 GB/s |
| 512 | 19,756 | 37.1% | 25.6 GB/s |
| 1024 | 39,209 | 73.7% | 51.2 GB/s |

The old decision was right about the bottleneck and wrong about the build: 64 lanes already wants more
than the board's DDR3 delivers, but fabric is not the scarce thing. **Build 256.** Any memory added
later becomes tokens with no re-synthesis. The 1024 row fits by logic count only — yosys does not place,
route or close timing, and 74% occupancy on a 7-series is where routing gets hard.

**One $60 chip at 512 lanes unpacks 25.6 GB/s against this entire eight-thread desktop's 10.55.**

### 4c. Reading and unpacking ADD on a processor

`plan.py` took the slower of the two. That assumes a chip does both at once; one core doing loads and
then shifts does not.

| | old rule | harmonic sum | measured |
|---|---|---|---|
| Teensy 4.1 | 33.9 MB/s | 18.2 | **21.4** |
| this desktop | 10.55 GB/s | 7.76 | **7.60** |

2% agreement on the desktop with nothing fitted. **Fabric is the exception** — it unpacks inside the
streaming datapath, on bytes already in flight — so the planner now carries an overlap flag, 1 for the
FPGA and 0 for every processor. That widened the FPGA's lead by arithmetic rather than argument.

### 4d. The tied head inverted the storage plan twice

First I put the 243 MB embedding table on the SSD, because input embedding reads one 4 KB row per token.
Wrong: the same tensor is the output projection, read in full every token, which on an SSD is seven
seconds a token. So it had to be in RAM — and then **the model no longer fit two boards**, one layer of
thirty-six homeless.

The way out is that the projection splits freely by vocabulary while a layer does not. Split two ways it
fits with room, and the input lookup goes back to the file after all, where it costs a tenth of a
millisecond and saves five layers' worth of RAM.

## 5. The hardware, finally measured

| part | reads memory | unpacks 4-bit | **sustains** | role |
|---|---|---|---|---|
| Zynq FPGA fabric | 2500 MB/s | 2290 MB/s | **2290 MB/s** | all the arithmetic |
| Luckfox Pico | 993 MB/s | 61 MB/s | 57 MB/s | move data, keep time |
| Teensy 4.1 + PSRAM | 33.9 MB/s | 39.3 MB/s | 21.4 MB/s | move data, hold small things |
| ESP32-S3 | 57.6 MB/s | ~11 estimate | ~9 | move data |
| this desktop | 29.40 GB/s | 10.55 GB/s | 7.60 GB/s | reference |

Also measured: Luckfox has **33 MB of RAM in total**, 15 available. Its SD card reads 17.7 MB/s cold and
writes 10.4. A Teensy's PSRAM reads 33.9 MB/s, confirming the earlier 32.8.

**One FPGA board is forty Luckfoxes or a hundred Teensys.** The microcontrollers are not slow helpers at
the same job. They are doing a different job.

## 6. The interconnect, measured between two machines

| payload | round trip | one way | MB/s |
|---|---|---|---|
| 64 B | 296 µs | 148 µs | 0.4 |
| 8 KB, one activation | 875 µs | 437 µs | 18.7 |
| 196 KB, a prefill batch | 12.3 ms | 6.2 ms | 31.9 |

437 µs against a stage taking 100–440 ms is under half a percent. **Cheap, not free**, and cheap is the
honest word now that loopback is not being quoted.

**This may save money: 18.7 MB/s over a plain USB cable is already enough.** The catch is shape — USB
gadget mode needs a host, so a star around one hub works and board-to-board does not. Ethernet buys
direct wiring, and speed nothing needs yet.

## 7. Four things about running it distributed that nothing warned me about

| change | decode | prefill |
|---|---|---|
| first working version, one request in flight | 1.55 | 1.59 |
| four requests in flight | 3.63 | — |
| cost-balanced layer split | 3.39 | — |
| no round barrier | 5.25 | — |
| prefill chunks pipelined | 4.99 | **6.94** |
| vocabulary-split head, 12 requests | **5.12** | — |

**One request in flight wastes every node but one.** The next token cannot start before the last exists,
so utilisation is 1/n and no hardware fixes it. The machine is a multi-request server.

**An even split is the wrong split.** The head was doing nine layers *and* the projection, 2.1× anyone
else, setting the pace for all four. Layers are now assigned by cost, and cost is not bytes: Q4_K
unpacks at 15.69 GB/s and Q6_K at 6.11, so the Q6_K projection hurt far more than its size suggested.
The head ends up holding **one** layer of thirty-six.

**A round barrier cost 55%.** "Send all k, receive all k, repeat" drains the pipe every round. Priming
and refilling on each arrival took utilisation from 51% to 96%.

**Batching prefill naively made it slower.** 4.98 tok/s one at a time, **2.91** batched, 8.87 with four
accumulators, 10.40 with eight. The obvious loop reloads the weight for every multiply and reached 9 of
this machine's 35 G MAC/s. Register-blocking over positions gave 3.6× with no change to the arithmetic.
Batched prefill now hits **93% of the machine's floating-point peak**, which is what makes prefill
compute-bound and gives the two GPUs in the brief a clear job: they are ~170× this CPU at it.

### The bug worth remembering

Batched prefill produced `Paris to capital capital capital`. The batch path was correct; the
single-activation path read a stale buffer. **Output that starts right and then degenerates means the
wrong memory is being read, not that a kernel is broken.** Found by adding a `--batch` flag and setting
it to 1, which moved the failure onto the first token and pointed straight at it. A knob that disables a
suspect path is worth more than an hour of reading.

## 8. Tooling traps, so nobody pays for them twice

- **`adb push` on the Luckfox image reports "1 file pushed" and writes nothing.** Do not trust it.
  `adb reverse` returns "error: closed". busybox there has no `nc`. It does have python3: send a listener
  as one `echo '<base64>' | base64 -d`, run it as a background task so the shell stays alive, and connect
  through `adb forward`. Verify with md5sum at both ends. Script at `scratchpad/push_luckfox.sh`.
- **A line-by-line loop feeding `adb shell` silently truncates** — adb eats the loop's stdin. Use
  `</dev/null`.
- **`export MSYS_NO_PATHCONV=1`** or Git Bash rewrites a remote `/tmp/...` into a Windows path.
- **Windows sends all 169.254 traffic out the lowest-metric interface**, a Tailscale tunnel here, so
  PC-to-board pings fail while board-to-PC works. Let the board be the client.
- **The Luckfox SD card is not mounted at boot**: `mount -t vfat /dev/mmcblk1p1 /mnt/sdcard`.
- **Arduino copies every source before compiling and the Teensy recipe has no extra-include hook**, so a
  sketch cannot reference shared code in place. `build.bat` refreshes copies from `shared/` on every
  build, which keeps one master.
- **yosys needs `oss-cad-suite/lib` on PATH** as well as `bin`, or it dies on a missing DLL.
- **Measure in `setup()` and reprint from `loop()`** on a microcontroller, or a serial monitor attached a
  second late finds an empty port.

## 9. Where it stands, and where it honestly loses

4.2× this desktop's usable bandwidth at the full fleet, and a desktop cannot be bought up to it: its
memory controller is soldered and its core count fixed. Sixteen FPGA boards supply 36.6 of that
43.8 GB/s; a hundred and twenty-eight Luckfoxes supply 7.4. **The microcontrollers are 92% of the node
count and 17% of the throughput.**

Against that:

- **On a 3B model this desktop wins**, 4.25 tokens a second against 2.27 for two boards. A model that
  fits one machine is the wrong test.
- **Capacity is the real limit.** Two boards hold 2 GB of fast memory; a 70B model needs about forty.
- **The 1 TB in the brief needs DIMM-capable FPGA boards.** These cannot take one: no FMC, the headers
  cannot make 1.5 V for SSTL15, six grounds per thirty-two signals.
- **Per-watt is an estimate**, roughly 13×, and wants a meter on both ends.
