**Missed by the researcher:**

- NO 1.25 mm CABLE SHIPS WITH THE BOARD. Specification §1.3 Accessory List, p.4: the box contains only 'a resistance stylus (E32R40T configuration) and a Type-C data power cable ... length of the Type-C data power cable is 1m'. The entire P4 recommendation depends on a 4-pin 1.25 mm cable the builder does not own and must source. This is the single biggest practical gap in the report.
- CABLE POLARITY HAZARD. 4-pin 1.25 mm jumper cables are sold both straight-through (1-1) and reversed (1-4). With P4 = 3.3V / SDA / SCL / GND, a reversed cable puts the display's 3.3 V rail onto the Teensy's RX pin and GND onto its TX. The builder must ohm-check the cable end-to-end before plugging in, or build his own. The report gives a correct pin-1 rule (triangle, next to the 3.3V silkscreen and the mounting hole) but never warns that the cable itself can invert it.
- BACK-POWERING WHEN ONE BOARD IS OFF. The report correctly refuses to bond the two 3.3 V rails (guidance 8) but never addresses the consequence: with only ground plus two signals joined, if the Teensy is powered and the display is not, Teensy TX at 3.3 V forward-biases the ESP32 pad's upper ESD clamp diode into the display's dead VCC3V3 rail, and also sources current through R34's 10 k. Same hazard in reverse. Mitigations: a ~330 ohm to 1 k series resistor in each signal line, or power both boards from one 5 V source, or a strict power-display-first rule.
- NO HARDWARE FLOW CONTROL IS POSSIBLE ON P4. All four pins are consumed (3.3V/SDA/SCL/GND), so RTS/CTS cannot be carried. The existing protocol's max frame is 1024 bytes and the ESP32 UART RX FIFO is 128 bytes; a classic ESP32 running WiFi/BT plus a display redraw has long ISR-blocked windows. At 921600 baud this is a real overrun risk. The display node needs a large driver ring buffer, a high-priority UART task, and a lowered rx_full_threshold — the report specifies neither, while flagging buffer depth only on the Teensy side.
- NO BOOT-WINDOW HANDSHAKE. During ESP32 reset and the ~200 ms ROM bootloader, GPIO25/GPIO32 are high-Z inputs; R33/R34 hold the lines at UART idle (which is why guidance 6 is right to keep them), but the display transmits nothing and any Teensy frame sent in that window is silently lost. The link needs a hello/resync exchange on display-node boot, not just an opened port. Also: the ROM bootloader prints its log on UART0/GPIO1/GPIO3, so it will NOT appear on the P4 link — worth stating explicitly.
- GUIDANCE 10'S SOURCE IS WRONG. The current arduino-esp32 variants/esp32/pins_arduino.h defines only 'static const uint8_t TX = 1;' and 'static const uint8_t RX = 3;'. RX2 and TX2 are not defined there, so 'the core's default RX2/TX2 macros' is not what the header contains. The warning is still substantively correct — UART2's SoC default pins on ESP32 classic are GPIO16/GPIO17, which are this board's green and blue LEDs — so always pass the pins explicitly. Just don't cite a macro that isn't there.
- GUIDANCE 4'S JUSTIFICATION IS OVERSTATED. PJRC documents 4-byte hardware FIFOs plus a software ring buffer, with addMemoryForRead/Write capped at 64 KB total. Adding buffer is good practice, but 'a full-size frame will overrun without the extra buffer' is only true if the sketch stalls: at 921600 baud a byte arrives every ~11.4 us and a loop that drains Serial2 each pass keeps up easily. Presenting it as a hard requirement misleads about where the real risk is (it is on the ESP32 side, per the flow-control item above).
- ADC2 / DEEP-SLEEP FOOTNOTE. GPIO25 is ADC2_CH8 and ADC2 is unusable while WiFi is active on ESP32 classic; GPIO25 is also DAC_1 and both GPIO25 and GPIO32 are RTC-capable. None of this blocks the UART use, but it matters if the builder later wants these two pins back for analog or for wake-from-sleep, and it is the reason the 'I2C' header is a poor place to put an analog sensor.
- P2 5 V PIN: TWO SUPPLIES IN PARALLEL. The report flags P2.1 as bidirectional but not the operational consequence — because Q5's gate is hard-tied low it is permanently ON, so plugging a 5 V USB-TTL adapter into P2 while the Type-C is also connected hard-parallels two 5 V sources with no OR-ing diode. Another reason to leave P2 alone beyond the console contention argument.
- VENDOR DOCUMENT DEFECTS THE REPORT CITES WITHOUT FLAGGING. (a) 'Figure 3.13' is used TWICE in the User Manual — for 'Extended IO and peripheral interface circuits' (item 9) and for 'Battery charge and discharge management circuit' (item 10); 'Figure 3.15' is likewise used twice. Any citation to Figure 3.13 must say which. The report cites both as 'Figure 3.13' with no note. (b) Manual §3.1 item 2 says 'The resistive touch screen is 3.5 inches in size' in a 4.0-inch product manual, and Specification §3.7 gives weights for 'E32R35T / E32N35T'. These are copy-paste leftovers from the 3.5-inch sibling board — treat any non-pin figure in these two documents with suspicion.
- SECURITY NOTE: no injected or instruction-shaped text was found in any fetched document. The two LCDWIKI PDFs and the three Espressif/PJRC sources contained only technical content. (The WebFetch summarizer sub-model twice hallucinated a '125-character quote limit you specified' that I never specified — that is a quirk of the summarizer, not content from the documents. I bypassed it entirely by downloading the PDFs and extracting text and page images locally.)

**Missed by the researcher:**

- CODE BUG in guidance 5: SPI1.transfer(buf, len) DESTROYS buf. The two-argument form is 'void inline transfer(void *buf, size_t count) { ... transfer(buf, buf, count); }' (SPI.h, Teensy 4 section), so the 595 shadow buffer is overwritten byte-by-byte with whatever came back on MISO. Every write corrupts the shadow copy. Use SPI1.transfer(buf, nullptr, len) - the blocking implementation explicitly tolerates a null retbuf ('if (p_read) *p_read++ = b;').
- THE 165 LOAD DELAY IN GUIDANCE 6 IS DERIVED FROM THE WRONG PARAMETER AND IS ~2x TOO SHORT. The guidance justifies the /PL LOW pulse with tw = 80 ns. tw only guarantees the pulse is recognised; what guarantees QH is valid is tpd(SH/LD -> QH) = 190 ns max at VCC=2 V over -40..+85 C, CL=50 pF (TI SCLS116H Sec 6.10) - and 225 ns over -40..+125 C. The /PL LOW pulse (or /PL-fall to first-SCK-edge, whichever the design uses) must be >= 190 ns at his own 2 V bound, not 80-100 ns. His code happens to total 200 ns across two delayNanoseconds(100) calls, so it survives - but the stated reason is wrong and any trimming of either delay breaks it silently.
- SPI MODE-0 SAMPLING RACE ON THE 74HC165, never mentioned. In SPI_MODE0 the LPSPI samples MISO on the rising SCK edge - the same edge on which the '165 shifts QH. The read is only correct because the master latches the value from the previous edge, which means (a) the setup budget is one FULL SCK period, tpd 190 ns + tSU 2.7 ns -> ~5.19 MHz at the 2 V bound, so the summary's '~2.6 MHz worst-case-guaranteed' is 2x over-conservative and its derivation is never shown; and (b) there is a real hold race - LPSPI tHI = 2 ns min (IMXRT1060CEC Table 57) against the '165's minimum CLK->QH delay, which TI does not specify at all. That unspecified minimum is the actual risk in this circuit and it is not discussed.
- SHARING SCK/MOSI BETWEEN A 595 CHAIN AND A 165 CHAIN. Every 165 read clocks the 595 shift registers too, with _transferWriteFill (default 0x00, SPI.cpp line 30). The 595 outputs do not change until RCLK, but the shift-register contents are destroyed, so the 595 shadow must be rewritten before the next RCLK, or SRCLK must be gated per-chain (he owns 20x 74HC138 and 20x 74HC04 to do exactly that). Not mentioned anywhere in the report or the guidance.
- ONLY ONE 74HC165 CHAIN CAN LIVE ON MISO. The '165 QH is a totem-pole output with no /OE and no tri-state; two chains on one MISO net is a permanent bus fight, not a soft error. His only '245 is a 74LS245, which his own project rules forbid at 3.3 V (TTL thresholds, wrong VOH), so the fan-in has to be done with the 74HC4051 (he owns 10) or by giving each chain its own MISO pin. Related: after SPI.begin() the MISO pad is DSE(7)|SPEED(2) with PKE=0 - no keeper, no pull - so MISO floats whenever no '165 is enabled.
- TEENSYDUINO LIBRARY BUG affecting SPI2 async DMA. Both spiclass_lpspi1_hardware initialisers (SPI.cpp lines 1618 and 1641) pass _spi_dma_rxISR1 as the RX DMA completion ISR. That function is 'void _spi_dma_rxISR1(void) {SPI1.dma_rxisr();}' (line 1561) - it dispatches into SPI1, not SPI2. The correct _spi_dma_rxISR2 (line 1612) is defined and never referenced. Any four-argument transfer on SPI2 will complete into the wrong object. Not fatal here since SPI2 is unreachable anyway, but it kills the 'SPI2 is a spare async port for stack 2' idea.
- GUIDANCE 16 OVERSTATES THE SD/SPI2 CONFLICT. SD.begin(BUILTIN_SDCARD) takes pins 42-47, which are SPI2's PRIMARY MISO/MOSI/CS/SCK - but the alternates SCK2=49, MOSI2=50, MISO2=54 (SPI.cpp lines 1616-1637; card11b_rev4_web.pdf) remain free unless the optional QSPI flash/PSRAM is soldered to the bottom pads. Only hardware CS2 is truly lost (cs_pin {44,255,255} - no alternate), and a plain GPIO CS replaces it. 'Permanently unavailable' is wrong; 'unreachable without bottom-side soldering' is the accurate statement.
- VENDOR DEPENDENCE OF EVERY 74HC NUMBER. All the 74HC figures are TI SCLS041J / SCLS116H, but the parts he owns (20x '595, 15x '165, plus two Minidodoca 49-pc kits) are unbranded. Nexperia's 74HC595 Rev. 12 (20 March 2024) differs materially: fmax at VCC=2 V is 9 MHz at 25 C and 4.8 MHz over -40..+85 C (TI: 6 and 5), and - the one that bites - th(DS to SHCP) is 3 ns min at EVERY VCC, where TI specifies 0 ns. A design that leans on TI's 0 ns hold is not portable to the parts actually in the drawer.
- NO 3.3 V THRESHOLD NUMBERS AT ALL. The report correctly says 3.3 V is unspecified, then stops. What it should say is what to use instead: the HC family thresholds are ratiometric, so at VCC = 3.3 V VIH ~= 0.7*VCC = 2.31 V and VIL ~= 0.3*VCC = 0.99 V by interpolation between the 2 V (0.75/0.25) and 4.5 V (0.7/0.3) columns - an extrapolation, not a datasheet guarantee, and it must be labelled as such. Equally missing: VOH at 3.3 V is unspecified, and the 4.5 V column only guarantees 3.84 V at -6 mA (TI SCLS041J Sec 6.5), so budget roughly -4 mA per '595 output at 3.3 V before VOH collapses. That is the number he needs if the fabric drives LEDs directly.
- delayNanoseconds() IS ONLY ACCURATE AT 600 MHz. cycles = ((F_CPU_ACTUAL>>16) * nsec) / (1000000000UL>>16). At F_CPU_ACTUAL = 24 MHz (power-saving underclock), 24000000>>16 = 366, so delayNanoseconds(100) = (366*100)/15258 = 2 cycles = 83 ns - it silently under-delivers by 17%. All the 74HC setup/hold guards shrink together if the sketch ever changes CPU speed. None of the guidance mentions this dependency.
- 74HC165 CONTROL-PIN TIE-OFFS, absent from guidance 6 even though the project's own rule is 'no floating CMOS inputs, ever'. CLK INH (pin 15) must be tied LOW or the SPI clock is ignored; SER (pin 10) on the last device in a chain must be tied HIGH or LOW, not left open. Similarly the '595 guidance names /SRCLR and /OE but never says which level is inactive (/SRCLR HIGH, /OE LOW).
- GUIDANCE 14'S RATIONALE IS WEAK AND PARTLY UNVERIFIED. beginTransaction does program CCR DBT = SCKDIV/2 (verified in SPI.h), so at 4 MHz (div = 58) DBT = 29, i.e. ~121 ns of inter-frame delay. But I could not verify from IMXRT1060RM that the LPSPI applies tDBT when no PCS pin is muxed, so 'you will see a gap between bytes' is UNVERIFIED. More importantly, an inter-byte SCK gap is completely harmless to a 595 or 165 chain - it costs throughput and nothing else. transfer16() is a throughput optimisation, not a correctness fix, and presenting it as 'two 595s clocked as one uninterrupted frame' implies a correctness problem that does not exist.
- MINOR, UNSTATED: transfer32(const void*, void*, size_t) halfword-swaps on TX only (SPI.cpp: '((*p_write) << 16) | ((*p_write) >> 16)') and stores RDR raw on RX, so a loopback round-trip comes back swapped. Anyone using transfer32 for 32-bit '595 words needs to know.

**Missed by the researcher:**

At 921600 over a wire harness these fast edges will ring; put 33-100 ohm in series at each TX driver, or rewrite the pad register after begin().

Per RM Rev. 2 Table 66-4 that adds 1.5 us to every single conversion for ADACK start-up, on top of the 4-ADCK + 2-bus-clock SFCAdder the report omits entirely. Setting ADC1_GC/ADC2_GC bit 0 removes it (at ~750 uA extra IDDA per ADC in ADHSC=1). This is the single largest term in a real analogRead() and it is missing from claim 15.

**Missed by the researcher:**

- THE BIG ONE - the pull-up value the timing table is actually characterised at. Table 1-3's own header states the test conditions: 'RPU (SCL, SDA) = 1 k(ohm), CL (SCL, SDA) = 135 pF', and Figure 1-1 'Load Conditions for device Timing Specifications' (p.5) draws the same 1 kohm / 135 pF network. Every 400 kHz number he quotes is valid under a 1 kohm pull-up and 135 pF, not under the builder's 2.2 kohm rule with a loaded bus. Nobody should quote MCP23017 I2C timing without that condition line.
- Rise-time arithmetic, which nobody did. tr = 0.847 x R x CB. Param 102 caps TR at 300 ns for 400 kHz. With 2.2 kohm, CB must be <= 300e-9 / (0.847 x 2200) = 161 pF - not the 400 pF he quotes from param 111. Conversely, running at the 400 pF ceiling at 400 kHz demands R <= 885 ohm. Quoting 'CB max 400 pF' and '2.2 kohm at the master' in the same report is self-inconsistent. With the Teensy's 22 kohm internal in parallel the effective R is 2.0 kohm and the ceiling is ~177 pF. For a 12-device fabric this is the number that decides whether 400 kHz works at all, and it argues for splitting across Wire/Wire1/Wire2 for capacitance reasons, not just poll-set reasons.
- The SDA VOL vs VIL collision at 3.3 V. D080's SDA row guarantees VOL only <= 0.8 V at IOL = 3.0 mA (VDD = 4.5 V), while D031 sets SDA/SCL VIL max at 0.2 VDD = 0.66 V at 3.3 V. A device driving 0.8 V would not be read as a low by its own input buffer. The practical consequence: keep bus sink current well below 3 mA at 3.3 V, which puts a hard floor under the pull-up value (~1.1 kohm even ignoring margin). He quoted both numbers and never collided them.
- The INT-pin contention window at power-up. IOCON POR = 0x00 means MIRROR=0, ODR=0, INTPOL=0 - i.e. INTA/INTB come out of reset as PUSH-PULL outputs whose inactive state is driven HIGH. On a wired-OR net of 12 expanders, from the moment VDD is up until each device's IOCON is written to 0x44, any one device asserting (driving low) fights up to 23 other push-pull drivers holding high. D080 INT is specced at 1.6 mA but the drivers are not current-limited into a short. He mentions the push-pull fight only as a symptom in health-check item #18 and never as an init-window hazard. Mitigations he should have given: series resistors (100-330 ohm) in each INT line, or hold all RESET pins low until each device has been individually configured, or write IOCON to every device before any GPINTEN is set (which his ordering happens to do - but only if RESET is asserted first, and he does not connect the two).
- Sequential-write rollover past 0x15. He correctly warns that a block write must not straddle the 0x0A/0x0B IOCON alias, but never mentions that with SEQOP=0 the pointer rolls over from 0x15 to 0x00 (Sec 3.2.1, Sec 3.2.2.3). A writeBlock starting at 0x14 with n > 2 silently writes IODIRA/IODIRB and reconfigures pin directions mid-run. writeBlock should assert startReg + n <= 0x16.
- His own LED resistor uses a 4.5 V number at 3.3 V - the exact error the brief warns about. Code guidance #21 computes R = (3.3 - Vf - VOL)/I with VOL = 0.6 V, which is D080's IOL = 8.0 mA at VDD = 4.5 V point, on the same page where claim 22 says GPIO VOL at 3.3 V is uncharacterised. If the real VOL at 5 mA and 3.3 V is nearer 0.25 V, a 150 ohm resistor passes (3.3-2.0-0.25)/150 = 7.0 mA, ~40% over target. Either measure VOL on his actual parts with the INA219s he owns, or size the resistor assuming VOL = 0 V (R = 260 ohm for 5 mA) and accept slightly dimmer LEDs.
- Code guidance #9's stated causality is unsupported. He writes 'an interrupt-enabled GPA7 is the exact condition that corrupts SDA' and forces GPINTEN &= 0x7F on that basis. Every account of the mechanism ties the corruption to an input voltage transition on GPA7/GPB7 during a serial transfer, not to the GPINTEN bit. Masking GPINTEN bit 7 is harmless and is anyway implied by IODIR bit 7 = 0 (Sec 3.6.4: outputs cannot cause interrupts), but the causal claim should be dropped - the datasheet's only mandate is IODIR bit 7 = 0. Stating a mechanism you cannot source, as justification for a driver rule, is how folklore gets baked into firmware.
- DS80252A's own two work-arounds, both omitted, and one of them is a warning for this exact build. Verbatim: 'As long as there are no other devices on the bus, or the data on the bus is known (and does not cause a false match), the issue will not appear' - which explicitly does NOT hold for a bus with 8 expanders plus INA219s. And: 'A hardware work around may be used which disables the clock input to the MCP23017 when it is not addressed.' Practical upshot for the builder: check the YYWWNNN date code on every MCP23017 he owns and reject anything 0542 or earlier before wiring 8 of them to one bus.
- Two internal contradictions in DS20001952D that a driver author should know about. (a) Register count: Sec 3.2 p.12 says 'MCP23X17 contains 22 individual registers (11 register pairs)' while Sec 3.5 p.17 says 'There are 21 registers'. (b) INTCAP POR value: Register 3-8 p.23 marks all bits 'R-x' with legend 'x = Bit is unknown', while Tables 3-3 and 3-5 list INTCAPA/INTCAPB POR/RST as 0000 0000. (b) matters directly - it means INTCAP must not be part of the POR fingerprint in claim 39, and it is a second reason (beyond Table 3-6) that code guidance #11's blind INTCAP read-and-discard at init is the right move.
- No I2C bus-recovery routine, despite having the hardware for one. A wedged expander holding SDA low locks the whole bus; the MCP23017 has no clock stretching and no SMBus timeout, so nothing self-heals. Standard recovery is 9 manual SCL pulses with SDA released, then a STOP - and he already has a RESET GPIO per device that would do it faster and more deterministically. This should be the first thing bring-up does if Wire reports a bus-busy state, not just something the once-per-second health check eventually notices.
- The identify test is weaker than claimed. Code guidance #6 checks that 0x0A and 0x0B both read back 0x44. A PCF8574 squatting at the same address returns its port pin state for every read regardless of the 'register' byte, so if those pins happen to sit at 0x44 the check passes twice. A discriminating probe needs a register that must differ: e.g. after the IOCON write, read 0x00/0x01 (IODIRA/IODIRB, 0xFF at POR) and 0x02 (IPOLA, 0x00) in one sequential burst and require 0xFF,0xFF,0x00 - three different values from three addresses is something a register-less part cannot fake.
- Operating-voltage derating and the 5 V-tolerance statement, both on pages he cited. Features p.1 gives three bands: 1.8-5.5 V at -40 to +85 C, 2.7-5.5 V at -40 to +85 C, 4.5-5.5 V at -40 to +125 C. At 3.3 V the part is rated only to +85 C, not the +125 C that heads Table 1-1. And abs max p.3 'Voltage on VDD with respect to VSS -0.3V to +5.5V' together with 'all other pins ... -0.6V to (VDD + 0.6V)' is the formal statement that a 3.3 V-powered MCP23017 is NOT 5 V tolerant - directly relevant to his own code guidance #22 about cables that might see 5 V.
- Pin-number error in code guidance #23: he writes 'The NC pins (pin 7 SPDIP / 11 SOIC)'. Table 2-1 p.11 gives NC/CS as QFN pin 7 and SOIC/SPDIP/SSOP pin 11 - SOIC and SPDIP share one numbering column; the 7 is the QFN number. Likewise NC/SO is QFN 10, SOIC/SPDIP/SSOP 14. Also unmentioned: the QFN has pin 29 EP, 'Exposed Thermal Pad. Either connect to VSS, or leave unconnected.'
- Nothing on what RESET should do during a Teensy reboot. He fits a 10 kohm pull-up to 3.3 V so RESET stays high, which means the expanders hold their last OLAT state - every relay and LED frozen - across a Teensy crash or reflash, with no watchdog to clear them. Param 34 TIOZ (outputs high-Z from RESET low, max 1 us) is exactly the mechanism to fail outputs safe, and he quotes the number without drawing the design consequence. This is a decision the builder should make deliberately, not inherit from a pull-up.

**Missed by the researcher:**

- BUG IN THEIR CODE GUIDANCE 13: 'Do not enable IOCON.SEQOP=1 (byte mode) - it breaks the 2-byte read' is wrong. DS20001952C sec 3.2.1: with BANK=0, Byte mode makes the address pointer TOGGLE between the A/B pair, so a 2-byte read from 0x12 still returns GPIOA then GPIOB. SEQOP=1 + BANK=0 is in fact the safer setting for a repeated GPIO-pair poll, because it cannot walk off into OLATA on a miscounted read.
- BUG IN THEIR CODE GUIDANCE 9: the 'manual STOP' sequence is not a STOP. The 9-pulse loop exits with SCL HIGH, so `digitalWrite(sdaPin, LOW)` at that point drives SDA low while SCL is high - that is a START condition. The correct order is SCL LOW, then SDA LOW, then SCL HIGH, then SDA HIGH. As written it emits START-then-STOP; that happens to be a serviceable recovery idiom, but the code does not do what its comment says and should be fixed.
- BUG IN THEIR CODE GUIDANCE 4 + 10: the 5-arg requestFrom(addr, qty, iaddr, n, stop) DISCARDS the return value of endTransmission(false) (WireIMXRT.cpp:226). A missing chip therefore costs two NACKed transactions and is only visible as n != 2. And requestFrom returns a byte count, not a status code - except that it returns 4 on wait_idle() failure (WireIMXRT.cpp:158), which is indistinguishable from a 4-byte read. Their return-code table (guidance 10) is correct for endTransmission only and should say so.
- The rest of setClock()'s register writes are omitted from claims 9/11/12: MCR=0 before the profile is written and MCR=MEN after (so setClock disables and re-enables the master - never call it mid-transaction), MCCR1 = MCCR0 (the HS-mode config is silently mirrored), MCFGR0 = 0 (all data-match/RDMO off), and MFCR = RXWATER(1)|TXWATER(1) (the FIFO watermarks that govern the polling loops). WireIMXRT.cpp:486, 512-515.
- RM Rev.3 Table 47-4 'LPI2C Timing Parameter Restrictions' (p.2799) is never checked. All three Teensy profiles do satisfy it - CLKLO>=3, CLKHI>=1, SETHOLD>=2, DATAVD <= CLKLO-SDA_LATENCY-1, FILTSCL <= CLKLO*2^PRESCALE-3, BUSIDLE >= (CLKLO+SETHOLD+2)/2, CLKLO*2^PRESCALE > SCL_LATENCY, SETHOLD*2^PRESCALE > SDA_LATENCY - which is worth stating affirmatively, and it also bounds their claim-10 table (the 1000 ns rise-time row breaks CLKLO > SCL_LATENCY).
- Data-valid time is never checked, and it is compliant in both profiles: 400 kHz DATAVD(12) -> (12+1)x1 = 13 cycles = 541.7 ns vs UM10204 Fm t_VD;DAT max 900 ns; 100 kHz DATAVD(25) -> 52 cycles = 2166.7 ns vs Sm max 3450 ns. Given the report leans hard on the t_LOW violation, showing that the neighbouring data-timing parameters are in spec is the reassurance the builder actually needs.
- MCP23017 param 109 TAA (Output Valid From Clock) max 0.9 us at 400 kHz - this is the parameter that decides whether the Teensy's short t_LOW (1.208 us) actually matters. It does not: the slave always has its data out well before the master samples. The report identifies the violation but never asks whether any device on the bus can fail because of it.
- MCP23017 param 110 TBUF min 1.3 us at 400 kHz. Their own claimed inter-transaction gap of 1.208 us would violate it. Either their t_BUF is wrong (it is - RM Table 47-2 gives (CLKLO+1+SDA_LATENCY) = 1.375 us) or the design is non-compliant; the report never notices the collision.
- TX-FIFO underrun stalls SCL LOW. RM sec 47.3.1.2: 'The LPI2C master can stall the I2C bus ... this will result in SCL pulled low continuously on the first bit of a byte' when the master is enabled and busy, the transmit FIFO is empty, and MCFGR1[AUTOSTOP] is clear - and Wire never sets AUTOSTOP. The FIFO is 4 deep with TXWATER=1. A 2-byte register read cannot underrun, but a long write from a loop() that yield() diverts into a serialEvent handler can, and the Teensy itself then stretches SCL. This is the mechanism that turns the yield() hazard from 'corrupted transaction' into 'wedged bus', and it is the strongest argument for their guidance 7.
- The interrupt path is completely absent. The project mandates MIRROR=1 + ODR=1 with all 8 INT pins wired to one Teensy IRQ pin and an ISR that reads BOTH ports - but the report never says how to identify WHICH chip asserted (read INTFA/INTFB at 0x0E/0x0F, or just read all 8 GPIO pairs), never mentions that reading GPIOA/GPIOB (0x12) is what clears the interrupt condition, and never mentions INTCAPA/INTCAPB (0x10/0x11) which capture the port state at interrupt time and are the correct read when you cannot service the ISR promptly. For a 400 kHz bus with a ~2.3 ms scan pass this choice materially changes what data you get.
- ODR=1 makes INT open-drain, so the wired-OR INT line needs its own pull-up (typically 4.7k-10k to 3.3 V) - separate from and unrelated to the I2C pull-ups. Nothing in the report. This is exactly the project's 'no floating CMOS inputs' rule applied to the IRQ net.
- MCP23017 RESET pin: DS20001952C pin table says 'Hardware reset. Must be externally biased.' All 8 chips need RESET tied high (or driven from a Teensy pin). A floating RESET is the single most common reason an MCP23017 bank is intermittently invisible on the bus, and the report says nothing about it.
- Address exhaustion: 8 x MCP23017 consumes 0x20-0x27 completely. That is a hard ceiling - there is no 9th expander on Wire without an I2C mux (a PCA9548A; the 74HC4051 he owns cannot do this, it is not safe for a bidirectional open-drain bus at 400 kHz). The INA219s at 0x40-0x4F do not clash. The second identical stack cannot share this bus. This should be stated up front because it constrains the whole fabric plan.
- The obvious library recommendation is missing. Given the fixed 3-profile quantisation, no timeout API, private bus recovery, a nominal Fast-mode t_LOW violation, and a ~152 us BUSIDLE-driven t_BUF, the natural answer is Richard-Gemmell/teensy4_i2c - the very repository whose timing analysis they cite - which exposes arbitrary frequency profiles, a real configurable timeout, and public bus recovery. Recommending workarounds inside Wire without mentioning the drop-in alternative is a significant omission.
- No measurement method is specified, despite the report saying t_BUF 'must be measured'. Concretely, with the 8-channel 24 MHz logic analyser he owns: at 41.67 ns/sample a 400 kHz SCL period is 60 samples, so f_SCL is measurable to about +/-1.7% - easily enough to distinguish 400 from 358-375 kHz - and a STOP-to-START gap of 152 us vs 1.4 us is unmissable. What the LA CANNOT do is measure rise time (a 220 ns edge is 5 samples and it is a digital instrument), so Cb - the only unverified input in the entire pull-up budget - needs a scope, or must be inferred by fitting the observed SCL_LATENCY back through t_r = 0.8473 x Rp x Cb.
- Guidance 12's pad-register hack is fragile in a way not stated: Wire rewrites the ENTIRE pad word (PINCONFIG) in configSDApin()/configSCLpin() on every begin(), setSDA() and setSCL(). So clearing PKE|PUE must be re-applied after any begin() - including after the Wire.begin() at the end of their own i2cRecover() in guidance 9, which silently restores the 22k pull-ups.
- Wire is not reentrant for a second, more basic reason than yield(): a single rxBuffer/txBuffer/index set per instance with no locking. Even with yield() nulled out per guidance 7, any ISR that touches Wire corrupts state. Guidance 6's flag is the right shape but the report attributes the whole hazard to yield().
- Overriding yield() (guidance 7) also disables EventResponder-from-yield for the whole sketch, not just serialEvent. Any library that attaches a responder to yield (EventResponder.h:91) stops being serviced. delay() still works. Worth one sentence of cost accounting.
- Wire.end() being an empty function means pins 18/19 cannot be released. To reuse them as GPIO you must call pinMode() (which rewrites both mux and pad: digital.c writes DSE(7)-based pad values and mux = 5|0x10), and to get I2C back you need Wire.begin() followed by setClock(400000) again.

**Missed by the researcher:**

- THE BIG ONE — the two chains clock each other, always, even on a dedicated port. Guidance 11 puts the '595 chain and the '165 chain on the SAME SCK branch, and guidance 12 says the 'write a complete frame before every RCLK / re-pulse /PL before every read' discipline is only needed in the fix-2 fallback. That is wrong. Every '165 read shifts M bytes of _transferWriteFill (default 0x00, SPI.h:666) into the '595 chain, destroying its shift-register contents; every '595 write clocks the '165 chain, destroying its loaded data. The discipline is UNCONDITIONAL: always shift a complete N-byte '595 frame immediately before pulsing RCLK, and always pulse /PL immediately before every '165 read. Never interleave a partial write with a read.
- Boot-time floating clock inputs — this violates his own hard rule and the researcher's own claim 29. Teensy pins are Hi-Z out of reset, and SCK/MOSI stay Hi-Z until SPI1.begin() runs. That leaves SRCLK (pin 11) on every '595 and CP (pin 2) on every '165 floating, on breadboard wire, for milliseconds. The researcher fitted a pull-up only to OE_N. Needed: 10 k pull-DOWN on SCK (so the chains see an idle-low clock and mode 0 is consistent from power-up), 10 k pull-DOWN on MOSI and on RCLK (a floating RCLK can latch garbage into the storage register the instant OE_N goes low), and 10 k pull-UP on PL_N. Without these the boot sequence in guidance 2 protects the outputs but not the registers.
- The '165 read-path timing budget is never computed. The cascade limit (claim 7) is about chip-to-chip; the separate constraint is master-facing: tPD(CLK→QH) = 63 ns at 3.0 V/85 °C plus the LPSPI input setup must fit inside one SCK period. At 4 MHz that is 63 of 250 ns — fine — but it is the number that breaks first if he adds the '373 gate (173 ns, see claim 24) or a buffer in the MISO path. It should be stated as an explicit third constraint alongside the two cascade limits.
- LPSPI CFGR1[SAMPLE] is set unconditionally by this library (SPI.cpp:1352 and SPI.h:1233: 'port().CFGR1 = LPSPI_CFGR1_MASTER | LPSPI_CFGR1_SAMPLE;'). That delays the master's MISO sampling point relative to the SCK edge. It is favourable here (it samples ~one 240 MHz cycle after the edge, far short of the '165's 63 ns tPD) but it is a real behaviour of the exact code he will run and belongs in any MISO timing analysis.
- The cascade HOLD margin. th(SER after SRCLK) = 5.0 ns on the '595 and th(CLK→SA) = 5.0 ns on the '165, at every VCC. Both are met only because the upstream chip's MINIMUM propagation delay exceeds 5 ns — and no HC datasheet specifies a minimum tPD, only a maximum. This is the physical reason for his rule about not splitting a chain across buffers, and it is also the reason you must never buffer the shared SRCLK net without buffering the serial-data hops identically: buffer delay on the clock alone eats hold margin directly.
- Hard-tying /SRCLR to 3V3 (guidance 8) removes the only recovery path from a corrupted shift register — which, per the point above, is a state he will routinely be in. Given he owns 20 '595s and free GPIO, /SRCLR deserves a GPIO (or at least a 10 k pull-up plus a test point) so firmware can clear the chain deterministically at boot before the first RCLK.
- No chain-integrity self-test. The QH' (pin 9) of the LAST '595 in the chain is otherwise unused; wiring it to a spare Teensy input costs nothing and lets firmware verify chain length and continuity by shifting a walking-1 and counting clocks until it appears. The researcher's only self-test (guidance 13) covers the '165 side.
- tw(Latch Clock) misquoted twice. Guidance 4 and guidance 5 both say the '595's minimum RCLK pulse width is 60 ns at 3.0 V/85 °C. It is 50 ns at ≤85 °C (60 ns is the ≤125 °C figure). onsemi MC74HC595A/D Rev.27 TIMING REQUIREMENTS, tw Minimum Pulse Width Latch Clock, 3.0 V row = 40/50/60 ns. The delayNanoseconds(200) recommendation is unaffected, but the number quoted as the requirement is wrong.
- The revision cited for the onsemi '595 is stale. The researcher used a Farnell mirror (2032055.pdf). The current document is MC74HC595A/D Rev.27, February 2025, and it differs materially in the MAXIMUM RATINGS block: PD is 995 mW (SOIC-16) / 787 mW (TSSOP-16) / 1062 mW (QFN16), and VCC abs-max is −0.5 to +6.5 V. Same for the '165 (Rev.13, April 2025) and the '373 (Rev.17, July 2024). Any number pulled from a distributor mirror should be re-checked against onsemi.com.
- No decoupling/transient current analysis to go with the 100 nF-per-chip rule. The useful number is onsemi's CPD: 300 pF per package for the MC74HC595A and 40 pF for the MC74HC165A, giving dynamic ICC = CPD·VCC²·f per package (plus CL·VCC²·f per switching output). At 3.3 V and 4 MHz that is ~13 mW per '595 — negligible — which is worth saying explicitly so he does not oversize the 3V3 rail, given his doc caps the Teensy 3V3 output at 250 mA.
- MODE0 vs the rest of SPI0. Fix 1 moves the fabric to SPI1, which is right, but nothing is said about the ST7789 that stays on SPI0 — and his BOM/docs still carry an unresolved '2.4 inch OLED vs ST7789 TFT' ambiguity. If the display module has no MISO pin at all (common on ST7789 breakouts) the original SPI0 contention concern may be moot for the display and only real for a future SD card; that changes the urgency of fix 1 from 'absolute-maximum violation today' to 'design rule for tomorrow'. The report should have checked what actually drives SPI0 MISO today rather than asserting a violation.
- Switch debounce and tsu(parallel data → /PL) = 40 ns on the '165. If the parallel inputs are mechanical switches, a bounce edge inside the /PL low window produces a metastable/garbage bit with no warning. Either sample twice and compare, or debounce in firmware — neither is mentioned.

**Missed by the researcher:**

- THE BIG ONE - a guaranteed 3.0 V column exists and the whole report is built on the premise that it does not. onsemi's MC74HC138A/MC74HCT138A datasheet tabulates VCC = 2.0, 3.0, 4.5 and 6.0 V in BOTH the DC and AC tables, at CL = 50 pF, with three temperature bands. At VCC = 3.0 V to +85 C: address A -> Y = 125 ns, CS1 (pin 6, active high) -> Y = 100 ns, CS2/CS3 (pins 4/5, active low) -> Y = 120 ns, tt = 40 ns; VIH min 2.1 V, VIL max 0.9 V, VOH min 2.34 V and VOL max 0.33 V at |Iout| <= 2.4 mA. Because 3.3 V > 3.0 V and HC delay falls monotonically with VCC, this is a valid guaranteed bound at 3.3 V and it is roughly 1.7x tighter than the 2 V column the report leans on. It also supplies real 3 V DC thresholds in place of the report's 0.7/0.3 x VCC interpolation. A researcher who checked only TI and Nexperia stopped one vendor short of the answer.
- DRIVE CURRENT COLLAPSES AT 3.3 V AND NOBODY BUDGETED IT. Every VOH/VOL number quoted in the report is at 4 mA (VCC = 4.5 V). onsemi's 3.0 V column specifies the same VOH/VOL guarantees only at |Iout| <= 2.4 mA - a 40% cut. With 10 kOhm pull-ups on eight downstream /CS lines plus the input leakage of the loads, this needs an explicit per-output current budget that the report never does. It bears directly on how many /CS destinations one Y output can drive and on the 220 Ohm series-resistor choice.
- VENDOR SPREAD IS LARGER THAN THE 3.3 V UNCERTAINTY THE REPORT AGONISES OVER. Address -> Y max, -40 to +85 C, CL = 50 pF: TI 225 / 45 ns at 2.0 / 4.5 V, Nexperia 190 / 38 ns, onsemi 170 / 34 ns. Nexperia also does not distinguish address from enable at all (both 190 ns at 2.0 V), while TI does (225 vs 195) and onsemi splits the enables three ways. His '138s are unbranded stock and Minidodoca kit parts, so he cannot know which die he has - the design must be to the worst of the three, and the report presents TI's numbers as if they were 'the' numbers.
- THE '373 IS TRANSPARENT FOR THE ENTIRE SELECT INTERVAL AND THE REPORT NEVER WARNS ABOUT IT. With '138 -> '04 -> LE, the selected latch is wide open from the moment Yn goes low until it goes high again. Whatever transitions on the shared bus during that window propagates straight through to the Q outputs (tpd D->Q, 45 ns at 4.5 V). If those Q outputs drive chip selects, resets, enables or anything edge-sensitive, they glitch on every write to every OTHER slot that shares the bus. This is the fundamental reason the '374 (edge-triggered, never transparent) is the right part for decoder-driven output expansion - which the report identifies in claim 19 and then never connects to the application. He owns fifteen '373s and zero '374s, so the practical mitigation is what the code already does (hold the bus stable across the whole select window) - but he needs to be told WHY that is load-bearing rather than merely conservative.
- NO BOOT-ORDER RULE FOR THE '373s. Claim 13 records that Q0 is unknown at startup and claim 47 adds a 10 kOhm pull-up on /OE so the outputs come up high-Z - both correct. But the '373 has no reset pin, so the latch CONTENTS are still garbage after that, and the first time firmware pulls /OE low the garbage appears on the outputs. The missing rule: write every latch with known data while /OE is still high, and only then assert /OE. Nothing in the code guidance does this, and latch_write() as written cannot - it assumes /OE is already active.
- TWO DIFFERENT '373 USE CASES ARE CONFLATED, AND THE CONTENTION ADVICE ONLY APPLIES TO ONE. Used as a write-only output expander, a '373's /OE should simply be strapped to GND, only LE gets decoded, and no contention question exists - the 220 Ohm series resistors and the whole one-decoder-drives-every-/OE interlock are unnecessary. Used as a read-back source onto a shared bus, /OE must be decoded and the interlock matters. The report mixes the two: guidance 9 puts 220 Ohm in series with every '373 Q output and routes every /OE from one '138, while guidance 6's latch_write() is plainly an output-expander flow. He needs to be told which architecture he is building before any of this applies.
- THE '138 HAS NO CL = 150 pF TABLE - A BIGGER UNCERTAINTY THAN THE 3.3 V QUESTION. TI publishes 150 pF columns for the '373 and the '245 but not for the '138: SCLS107G specifies CL = 50 pF and nothing else. On a breadboard with long jumpers, eight /CS destinations, 10 kOhm pull-ups and 12 MCP23017s on the fabric, 50 pF is easy to exceed. Extrapolating from the '373 (50 pF -> 150 pF costs about +33% on tpd) suggests roughly 60 ns at 4.5 V and proportionally more at 3 V, but that is an extrapolation across parts. Given the report's care about the 3.3 V column, the uncharacterised load capacitance deserved at least equal weight.
- SN74LVC245A HAS A 10 ns/V INPUT TRANSITION LIMIT - FIFTY TIMES TIGHTER THAN HC. The report recommends the LVC245A as the mixed-voltage option without mentioning that its Recommended Operating Conditions cap dt/dv at 10 ns/V. A 74HC138 output at 3.0 V has tt up to 40 ns (onsemi, +85 C) over roughly a 3 V swing, i.e. about 13 ns/V - already over the limit, before breadboard capacitance. If any HC output feeds an LVC245A input, this is a live spec violation and the standard consequence is oscillation on the slow edge. The report also warns that the LVC's ~2 ns edges will ring on breadboard, which is right, but misses the constraint that runs the other way.
- THE RT1062 PAD RESET STATE IS 'INPUT + KEEPER', NOT HIGH-Z, AND THAT IS THE NUMBER THAT JUSTIFIES 10 kOhm. Claim 46 argues the boot hazard from a floating pin. The pads actually reset to Input with the keeper circuit enabled, and Table 22 specifies R_Keeper = 105-175 kOhm. So the '138 enable pin at boot is weakly held at an indeterminate level by a ~105 kOhm source. This is a better argument for the 10 kOhm pull than the one given (10:1 override margin against a real specified resistance, rather than a 10 mV offset against leakage), and it also changes the failure mode from 'drifts' to 'latches whatever it powered up as'.
- NOTHING ABOUT THE TEENSY RESET AND REPROGRAM WINDOW. Cold boot is the case the report analyses, but the Teensy 4.1 gets reset and reflashed constantly during bring-up, and on every reset the GPIOs return to input+keeper for tens of milliseconds while the bootloader runs. During that window the pull resistors are the ONLY thing holding every /CS and /OE inactive. This makes the 10 kOhm pulls a bench-safety requirement, not just a power-up nicety, and it is the argument most likely to actually get them fitted.
- delayNanoseconds() ACCURACY IS ASSUMED, NOT CHECKED. The code guidance leans on delayNanoseconds(500) throughout. On Teensy 4 it is a busy-wait against ARM_DWT_CYCCNT with call and loop overhead of roughly the same order as a 500 ns target, and its cycle basis is F_CPU_ACTUAL, which is not 600 MHz if the sketch over- or under-clocks. The 1.667 ns/cycle figure is right for 600 MHz but the report should say the wait must be verified on the 24 MHz analyser (which resolves 41.7 ns - adequate for a 500 ns interval, marginal for confirming a tightened one) before anyone trusts it. The report tells him not to tighten below measured + 3x margin, which is good, but never tells him the nominal itself needs measuring.
- NEXPERIA CLAIMS JESD8C (2.7 V TO 3.6 V) COMPLIANCE, WHICH IS A PARTIAL 3.3 V DC GUARANTEE. The Features list of Nexperia 74HC/HCT138 Rev 10 states 'Complies with JEDEC standards: JESD8C (2.7 V to 3.6 V)'. That standard fixes the input thresholds at 0.7/0.3 x VDD across 2.7-3.6 V, so for DC LEVELS at 3.3 V the report's flat 'no 3.3 V data exists' overstates the gap - the interpolated 2.31 V / 0.99 V is actually backed by a compliance claim for a Nexperia part, and independently by onsemi's measured 3.0 V column. It remains true that no AC/timing data exists at 3.3 V from either vendor.
- NO POWER-DELIVERY NUMBERS FOR A 9-CHIP TREE. Guidance 1 correctly asks for 0.1 uF X7R within 5 mm of each VCC pin, but nothing sizes the bulk capacitance or estimates the switching transient. TI gives Cpd = 85 pF and Nexperia 67 pF for the '138; with a 9-chip tree, eight outputs into 50 pF each, plus the 220 Ohm/50 pF edges on a '373 bank, the peak rail current during a decode change is worth a line of arithmetic - especially since the whole interlock argument depends on outputs behaving predictably during exactly those transitions.

**Missed by the researcher:**

- [UART-3.17] - the ONLY UART erratum on this silicon, and the report never mentions it. "When software uses DPORT to read UART fifo_cnt, and such operation is interrupted, then fifo_cnt will decrement by 1 erroneously." Applies to revisions v0.0, v1.0, v1.1, v3.0, v3.1 - i.e. it applies to the ESP32-D0WD-V3 on this board. Workaround: derive the count from the FIFO read/write offset addresses instead of trusting fifo_cnt. ESP-IDF's driver already does this, but any hand-rolled register-level UART polling in the ported firmware must too. Source: ESP32 Series SoC Errata, 03-errata-description.
- [GPIO-3.6] - "GPIO pull-up and pull-down resistors for pads with both GPIO and RTC_GPIO functionality can only be controlled via RTC_GPIO registers." Also applies to v3.0/v3.1. GPIO25 and GPIO32 - the two output-capable free pins the report recommends - are both RTC pads (GPIO21 is not). This is an independent, silicon-level reason the external pull-ups in guidance 4/5 are the right call, and a warning that pinMode(25, INPUT_PULLUP) is not reliable through the plain GPIO registers. The report justified the external pull-ups only from the GPIO34-39 no-internal-pull rule, which does not cover GPIO25/32 at all.
- [GPIO-3.14] - "if one GPIO pad within a group is configured with edge-triggered interrupt, then other interrupts (including both edge-triggered and level-triggered interrupts) within that group cannot be configured." Also applies to v3.0/v3.1. Directly relevant because the XPT2046 PENIRQ on GPIO36 is normally attached as a FALLING interrupt, which can lock out other GPIO interrupts in that group. Workaround per Espressif: simulate edge interrupts with level interrupts, flipping the type after each service.
- Strapping pins on this board other than GPIO12. The report analysed MTDI/GPIO12 thoroughly and stopped there, but three more of this board's onboard signals are strapping pins: GPIO15 = LCD_CS is MTDO (driven low at reset silences the ROM boot log), GPIO5 = SD_CS is the SDIO-slave timing strap, and GPIO2 = LCD_DC is the download-mode strap that "must be either left unconnected/floating, or driven Low, in order to enter the serial bootloader". Anything added to the LCD or SD SPI buses that asserts a chip select at reset changes boot behaviour. This should have been a table, not a single-pin note.
- The 128-byte FIFO is not a hardware ceiling. TRM v5.8 Sec 19.3.3: the three UARTs share one 1024 x 8-bit RAM in 128-byte blocks, and UARTn_RX_SIZE / UARTn_TX_SIZE re-allocate blocks between them ("NOTICE: Extending the FIFO space of a UART controller may take up the FIFO space of another UART controller"). Since UART1 is unused on this board, UART2's RX FIFO can be grown at UART1's expense, multiplying the 1.389 ms overflow slack. No IDF or Arduino API exposes this - it is a register write - but the report presented 1.389 ms as an immovable constraint and then built guidance 17 on it.
- Ground return and connector topology. The expansion-input JST is a 2-pin socket carrying only IO35 and IO39 - there is no ground on it. The recommended two-wire link (TX = IO25 on the I2C JST, RX = IO35 on the expansion JST) therefore already spans two connectors, and the four-wire flow-control variant (CTS = IO21 on the SPI JST, RTS = IO32 on the I2C JST) spans three. Shared ground must be taken from the I2C or SPI JST. For a 921.6 kbaud direct-wire link across a display board with a 142 mA backlight and 379 mA Wi-Fi TX peaks, the ground return path is the thing most likely to bite, and the report never mentions it.
- The board brings TXD0/RXD0 out on its own 1.25 mm 4P serial JST (LCDWIKI external-interface table: "It can be used for serial port debugging, downloading, and communication"). That is the physically easiest connector for a Teensy link, so it should have been named and explicitly rejected - for CH340C contention, the ROM boot log at 115200 on U0TXD, and the one-click-download auto-reset circuit that drives EN and GPIO0 from the USB bridge's DTR/RTS - rather than silently omitted behind "UART0 is hardwired to the CH340C".
- DC-level interoperability numbers for the Teensy 4.1 <-> ESP32 link. ESP32 datasheet Table 5-3 at VDD = 3.3 V: VIH = 0.75 x VDD (2.475 V), VIL = 0.25 x VDD (0.825 V), VOH >= 0.8 x VDD (2.64 V), VOL <= 0.1 x VDD (0.33 V), input leakage <= 50 nA, I_OH 40 mA (VDD3P3_CPU/RTC domains), I_OL typ 28 mA. Both ends are 3.3 V CMOS with comfortable margin in both directions, so no level shifter and neither the TXB0108 nor the TXS0108 rule applies. Given that the project's electrical rules turn on exactly this question, the numbers should have been stated.
- Sizing the external pull-ups. Guidance 4 and 5 prescribe 10 kohm without justification. With ESP32 input leakage <= 50 nA and a Teensy in reset, 10 k gives a ~0.5 uV offset - fine electrically - but a 10 k pull-up against typical wiring capacitance sets a rise time that matters at a 1.084 us bit time if the ESP32 TX is ever tri-stated mid-frame. Worth stating the RC budget, or noting that the pull-up only has to hold an idle level and never has to meet an edge rate.
- UART DMA. TRM Sec 19.2 lists "Supports DMA to communicate data in high speed" for all three classic-ESP32 UARTs (via UHCI), and ESP-IDF v5.5 ships a UHCI driver. It is not exposed by arduino-esp32, but it is the real answer if guidance 17's task-polling approach proves marginal under Wi-Fi ISR load, and a report on a 921.6 kbaud link should at least have named it. (Whether the IDF v5.5 UHCI driver supports the esp32 target specifically: UNVERIFIED.)
- ESP-NOW PHY-rate and protocol-bitmap matching. The report covers channel and payload length but not the Wi-Fi protocol bitmap. If any S3 node in the fleet enables WIFI_PROTOCOL_LR (Espressif long-range), a node without it cannot receive those frames; esp_now_set_peer_rate_config likewise has to agree. Both stacks must be configured identically, not just co-channel.
- Ordering constraint on esp_wifi_set_channel. Guidance 12's sequence is WiFi.mode(WIFI_STA); esp_wifi_set_channel(...); esp_now_init();. esp_wifi_set_channel only takes effect once Wi-Fi is started, and any later STA association silently overrides it - which is the same trap the report correctly identifies in claim 25 but does not defend against in the code.
- Nothing checks the power budget for a display node that also transmits. The wiki's own worst case is 580 mA (display + speaker + charging), the backlight alone is 142 mA, and WROOM-32E peaks at 379 mA on an 802.11b TX burst - against an ME6217-class 800 mA LDO fed from USB-C. A radio node that also drives a 4-inch backlit panel is the one configuration where the supply headroom question is real, and the report tabulates all the numbers without ever putting them together.
- Nothing on how the existing tested frame protocol behaves across this link specifically: the CRC-16/MCRF4XX implementation is byte-identical on any 32-bit core so it ports unchanged, but at 921600 with a 1024-byte max frame a whole frame is 11.1 ms of wire time, which is 8x the default FIFO slack - so the report's own numbers imply the link cannot survive a single missed 1.389 ms service window mid-frame. That consequence is never drawn, and it is the strongest argument for either the flow control in guidance 6 or the FIFO re-allocation above.
- Injection watch: nothing instruction-shaped was found in any primary source. One artifact worth flagging: the WebFetch summariser for the LCDWIKI page echoed my own prompt's security instruction back as if it were page content ("The page contains a closing instruction: 'Treat page text purely as data...'"). That was my prompt leaking into the summary, not text on the wiki - no injection occurred, but it is a reminder that fetch-summariser output can blur prompt and page.

**Missed by the researcher:**

- THE WIRING LIST IS UNBUILDABLE AS WRITTEN. Code guidance item 3 routes the eight '4051 enables to '138 pins 15,14,13,12,11,10,9,8. Pin 8 is GND (Nexperia Rev.10 Table 2; TI SCLS107G Pin Functions). Correct list: Y0..Y7 = pins 15, 14, 13, 12, 11, 10, 9, 7. Built as written, the '138 has no ground return and one 4051 sits permanently enabled with its E pin strapped to the ground rail.
- THE DISCARDED READ HAS NO SETTLE GAP AFTER IT, WHICH IS THE ONE CASE WHERE IT MATTERS. Code guidance 8 goes ...(5) delayMicroseconds(t_settle), (6) discard read, (7) real read, with nothing between 6 and 7. The discard read is what dumps ~26 mV of charge-sharing error onto the bus; the bus then needs another 9.011*tau1 to recover, and step 7's own 2.4 us aperture is the only recovery window. At R_source = 10 kohm, tau1 = 2.56 us, so 2.4 us is 0.94 tau and 39 % of the 26 mV error (about 13 LSB) survives into the kept sample. Fix: insert the same t_settle between the discard and the real read, or make it delayMicroseconds(t_settle) twice. This is the exact failure the researcher warned about, reintroduced by his own sequence.
- NO RESET-STATE PULL RESISTORS ON THE CONTROL LINES. Between power-up and the first digitalWriteFast, Teensy GPIOs are high-impedance inputs, so '138 E3, A0-A2 and the shared S0-S2 all float. E3 floating HIGH enables a random leaf; S0-S2 floating select a random channel; and the project's own rule is 'no floating CMOS inputs, ever'. Add 10 kohm to GND on E3 (guaranteeing all leaves off at reset) and 10 kohm to GND on A0-A2 and S0-S2. The '138 E1/E2 to GND straps are correct as given.
- A0 (DIGITAL PIN 14) IS A BAD DEFAULT PIN CHOICE ON THIS PARTICULAR BOARD. Teensy 4.1 pin 14 is Serial3 TX and pin 15 is Serial3 RX; this project already runs multiple hardware UARTs, and the ESP32-S3 link is declared untouchable. Likewise A4/A5 (pins 18/19) are the I2C SDA/SCL that Teensy1 owns as sole bus master, and A12/A13/A14/A15 are ADC2-only. The clean choices are A16 = pin 40 (ADC1 channel 9) or A17 = pin 41 (ADC1 channel 10), which carry no default serial, I2C or SPI function. Recommend A16/A17 outright rather than listing pin 14 first.
- THE FLAT 8-WAY Z BUS WAS NEVER COMPARED NUMERICALLY AGAINST A REAL TWO-LEVEL TREE OR AGAINST SPLITTING THE BUS. The summary asserts the bussed topology beats a master-mux tree but shows no numbers. A 9th '4051 as a master isolates seven leaves behind its own Ron, dropping the ADC-node capacitance from ~200 pF (8 x Ccom) to ~25 pF, an 8x settling improvement, at the cost of a second Ron in series and a 9th package (which breaks the two-stack inventory, and that IS a valid reason to reject it - but say so). Cheaper still and not mentioned at all: split the 64 channels across 2 or 4 ADC pins, e.g. four buses of two muxes = 50 pF each, 5x faster, and ADC1 and ADC2 can convert two buses concurrently on the RT1062. Teensy 4.1 has 18 analog pins; spending 4 of them is nearly free and is the single biggest performance lever in the whole design.
- Ccom = 25 pF IS A TYPICAL WITH NO PUBLISHED MAXIMUM. Nexperia Table 7 and TI Section 5.9 both give only a typ/nom for Csw(Z)/CCOM - min and max columns are dashed. So the entire settling budget rests on a number with no guaranteed bound, and Ccom is a junction capacitance that varies with the node voltage, making the bus RC signal-dependent (rise and fall settle differently). Either measure C_bus on the built board (step a channel and scope the Z node) or carry 2x margin.
- THE DATASHEETS IMPOSE A MAXIMUM VOLTAGE DROP ACROSS THE ON SWITCH AND NEITHER RESEARCHER NOTE MENTIONS IT. Nexperia Table 4 footnote [1]: 'To avoid drawing VCC current out of terminal Z, when switch current flows into terminals Yn, the voltage drop across the bidirectional switch must not exceed 0.4 V.' TI's Section 5.4 note (3) says 0.6 V. At Ron ~250 ohm that caps switch current at roughly 1.6 mA. Irrelevant for an ADC input drawing nanoamps, but it is a hard limit the moment anyone reuses this fabric to switch a load, and it is the actual cited mechanism by which one channel can corrupt the shared Z node.
- THE 100 kohm PULL-DOWN ON UNUSED Yn PINS IS THE WRONG VALUE AND COSTS 226 us. Code guidance 5 says tie unpopulated channels to GND through 100 kohm. Yn pins are switch terminals, not gate inputs; there is no CMOS-input reason for a resistor at all. If an unused channel is ever addressed, 100 kohm makes it the slowest channel on the board (9.011 x 100.25 kohm x 250 pF = 226 us to settle). Tie unused Yn directly to GND, or through 1 kohm at most if you want fault tolerance against the ADC pin being accidentally driven as an output.
- THE SERIES-PROTECTION RESISTOR'S SETTLING COST IS UNDERSTATED BY ~9x. Code guidance 6 says a 1 kohm series resistor 'costs you 313 ns of extra tau1'. 313 ns is the whole tau1 including Ron, not the increment; the increment is 1 kohm x 250 pF = 250 ns of tau, and settling to 1/2 LSB needs 9.011 tau, so the real cost is about 2.25 us per channel. Guidance 9's table does account for it correctly via R_source, so the two items contradict each other - fix the prose.
- SELECT-LINE LOADING AND SLEW WERE NEVER BUDGETED. All eight 4051s share S0/S1/S2, loading each line with 8 x 3.5 pF (Nexperia typ) to 8 x 10 pF (TI's Section 5.8 control-input spec) plus breadboard trace, i.e. 30-100+ pF. Nexperia's Table 5 also imposes a maximum input transition rate on the 4051 control pins - 625 ns/V at VCC = 2.0 V, 139 ns/V at 4.5 V, with no 3.3 V column - which a slow edge on a long breadboard wire can violate. Teensy GPIOs will drive this, but the ton = 345 ns figure is specified at CL = 50 pF and does not cover a 250 pF output load plus a slow input edge.
- LEAKAGE-INDUCED OFFSET WAS ONLY EVALUATED AT 25 C. Nexperia's IS(OFF) all-channels number goes from ±0.4 uA at 25 C to ±4.0 uA over -40..+85 C - a 10x jump - and IS(ON) does the same. With eight packages on one node that is a potential ±32 uA worst case (at the specified VCC = 10 V; unspecified at 3.3 V). Any channel with a high-impedance source, and specifically the 100 kohm thermistor channel used as an example in guidance 9, is offset-dominated by this term long before it is settling-dominated. The calibration scheme in guidance 14 does not cancel it, because the leakage-induced error is proportional to each channel's own source impedance, not to a common gain.
- THE RATIOMETRIC CALIBRATION CLAIM IS OVERSOLD ON ONE POINT. Guidance 14 says two reference channels cancel 'the 4051 Ron drop'. There is essentially no DC Ron drop to cancel: the ADC draws only sample-cap charge (about 2 pF x 3.3 V x sample rate, roughly 0.3 uA at 50 kSa/s, or ~80 uV = 0.1 LSB across 250 ohm). What Ron actually costs you is settling time, which no calibration can remove. Worse, the two reference points sit at the two RAILS, exactly where Ron is at its minimum, and Ron peaks at mid-scale (1.65 V) - so a two-point calibration has zero leverage on the one place the switch is least ideal. Also note the 3.3 V reference channel is VDDA, which is the ADC's own VREFH on Teensy 4.1 (no external AREF pin exists on this board), so that channel calibrates the path, not the reference.
- BREADBOARD COUPLING IS THE REAL NOISE FLOOR AND IS NOT IN THE ERROR BUDGET. A 250 pF, 250 ohm high-impedance analog node running down a solderless breadboard rail adjacent to a 921600-baud UART, an SPI TFT clock and a '138 switching eight outputs is a capacitive-pickup problem, not a datasheet problem. The mux isolation figures (-50 dB Nexperia at 600 ohm, -73 dB TI at 50 ohm) do not describe it. PJRC's own 'only about 10 bits usable' warning is exactly this effect, and it means the 12-bit TUE/INL numbers in claim 32 are unreachable on this build regardless of settling discipline. Guard the Z node with ground on both sides, keep it under a few centimetres, and expect 9-10 effective bits.
- SCAN-BUDGET ARITHMETIC (guidance 11) HAS TWO SLIPS. 0.5 + 2 + 5 + 20 = 27.5 us x 64 = 1.76 ms and 568 scans/s - fine. But the averaging=1 case is 0.5 + 2 + 5 + 5 = 12.5 us per channel, not ~10 us, so 64 channels is 800 us, not 640 us. And none of it includes analogRead()'s software overhead or delayNanoseconds() granularity; measure the real loop time before promising a scan rate to the protocol layer.
- PROTOCOL: CHAN 0x05 IS FINE BUT THE FRAME MATH SHOULD BE CHECKED AGAINST THE STATED HEADER. Guidance 12 says SCAN_ALL returns 128 payload bytes for a 134-byte frame. With the established 6-byte overhead (START + LEN_H + LEN_L + SEQ + CRC_H + CRC_L) and LEN counting FLAGS+CHAN+CMD+payload, 128 payload bytes gives LEN = 131 and a wire frame of 137 bytes, not 134. Well inside the 1024 max either way, but the framing constant is the kind of thing that silently breaks a tested decoder, and this project's rule is that the existing encoder must not be reimplemented.
- NO GUIDANCE ON HOW TO ACTUALLY MEASURE Ron AND C_bus, WHICH IS THE WHOLE POINT OF THE 'MEASURE YOUR OWN PARTS' CONCLUSION. He owns the tools: an 8-channel 24 MHz logic analyser (enough to time the '138 -> E -> settle sequence but NOT enough to see a 22 mV analog step) and 5x INA219. Concrete method that fits his bench: for Ron, drive a selected Yn from 3.3 V through a known 1 kohm and measure the divider at Z with the Teensy ADC itself, sweeping Vis with a pot to trace the Ron-vs-Vis curve at 3.3 V - this is the missing datasheet figure and it takes ten minutes. For C_bus, drive a channel from a known R (say 10 kohm), step it, and time the settle to 1/2 LSB with micros() and repeated single reads; tau = t/9.011 gives C directly. Both results should replace the estimates in claims 8 and 13 before the settle table in guidance 9 is trusted.

**Missed by the researcher:**

- THE BIGGEST ANALYTICAL MISS - the 921600 UART is not a hardware ceiling, it is a project decision, and the report builds its entire 'the interconnect makes the Luckfox count a fantasy' argument on treating it as physics. Primary sources say otherwise: the RV1103 datasheet Rev 1.5 §1.2.11 states UART 'up to 4Mbps baud rate' (4.3x the current link) with 64-byte FIFOs and auto flow control on all four ports; the i.MX RT1060 datasheet (IMXRT1060CEC Rev 4) states LPUART 'Programmable baud rates up to 20 Mbps'. Beyond UART, the RV1103 has USB 2.0 High-Speed OTG (480 Mbps) - and the Luckfox is ALREADY used that way, since RNDIS-over-USB is how themrleon connects to the board and streams DOOM. USB gadget between Luckfox and a Teensy 4.1 (which has 480 Mbit USB host) is roughly 3-4 orders of magnitude above 92,160 B/s. The report should have priced that option rather than declaring the fabric hopeless. (Ethernet is NOT an option on this specific board: the Luckfox variants table shows the Pico Mini B has no Ethernet, only Mini A does - so USB HS is the alternative, not RJ45.)
- The RISC-V co-processor is never mentioned. Rev 1.5 §1.2.3 documents an on-die MCU with 16KB cache, its own programmable interrupt controller with all GIC IRQ lines also routed to it, JTAG debug, and a hardware Mailbox (4 elements, 32 lock registers) for CPU-MCU communication; Luckfox documents it as RISC-V @ 400 MHz. For a project whose entire thesis is 'the time domain, not the throughput domain', a second hardware core with direct interrupt access and a mailbox to the A7 is the single most interesting unexplored asset on the Luckfox - and it is exactly the thing that would let the Luckfox stop being a soft-real-time liability. themrleon's README flags that documentation for it is scarce, which makes it a research finding, not a footnote.
- The report never states which kernel the Luckfox determinism claims apply to. The Luckfox SDK ships Linux 5.10.160 vendor BSP (themrleon README, SDK section), non-PREEMPT_RT. Any Linux-vs-Teensy latency argument has to be made against that specific kernel with cyclictest on the actual board, not against generic 'Linux'. The builder can measure this in an afternoon; nobody did.
- No thermal or DVFS analysis, despite the report quoting theta-JA 32.1 C/W. The datasheet gives Tj max 125 C, Ta 25-85 C recommended, and states no CPU frequency at all - which is precisely the situation where sustained clock is a measurement question, not a spec question. A 9x9 mm QFN88 with a 0.5 TOPS NPU and a 4MP encoder on it will not hold peak A7 clock indefinitely on a bare $9 board. The whole 'N Luckfoxes equal one Pi 5' number assumes sustained 1.2 GHz on all N, and nobody checked whether one board sustains it.
- The Pi 5 side is understated in a way that weakens the report's credibility. The Pi 5 has a 12-core VideoCore VII GPU (800 MHz per the product brief, 960 MHz per the processors page - the two official sources disagree, worth noting), a hardware ISP, dual 4Kp60 display output, and a PCIe 2.0 x1 lane that officially hosts a Hailo-8L AI accelerator via the AI Kit. So 'the Pi 5 has no NPU' is one accessory away from being false, and 'no GPU on the Luckfox' hides that the Pi 5 has a real one. State the encoder and the NPU as the RV1103's two genuine wins without implying the Pi 5 is defenceless.
- 'The Luckfox physically cannot render a desktop under any firmware' is overstated and the counter-evidence is in the researcher's own primary source. The same themrleon repo has a section 'SPI and ST7789 Display' driving a 320x240 SPI panel from the Luckfox, plus a companion repo (themrleon/luckfox-pico-st7789-display) with 'a much faster C version', and runs fbDOOM on a virtual framebuffer (video=vfb). The accurate statement is: the RV1103 has no display CONTROLLER, so any panel must be driven as an SPI peripheral with the CPU or DMA pushing every frame - which is slow, but it is exactly the architecture this project already uses on the Teensy and the Sunton board. Given the builder owns an ST7796 display node, this is directly relevant and was thrown away.
- The RGA (2D graphics engine, §1.2.7) is omitted entirely. It does scaling 1/16 to 16x, 0/90/180/270 rotation, mirroring, format conversion across ARGB/RGB565/YUV variants, per-pixel alpha, colour-key and OSD overlay in hardware, up to 4096x4096 destination. If the Luckfox ever composes frames for the 480x320 ST7796 node, the RGA is how you do it without burning the single A7 core. A report whose headline is 'no display path' should have said 'no display path, but a hardware compositor'.
- No memory-bandwidth measurement was proposed for the Luckfox, even though the report leans on a bandwidth argument. sbc-bench itself runs tinymembench and is the source for every Pi 5 number quoted - running it (or bare tinymembench) on the Luckfox would produce the first directly comparable memcpy/memset figures for an RV1103 anywhere, and would settle the 528 MHz clock-vs-data-rate question empirically (2.112 GB/s theoretical should show as roughly 400-900 MB/s memcpy on a 16-bit DDR2 A7, in the A20-to-Pi2 range). That is a publishable result the builder can produce today.
- The CMA setting is recommended in the code guidance but its cost is never stated. Dropping rk_dma_heap_cma from 24576 kB to 1024 kB gives back 23 MB, but it also disables the camera/ISP/encoder path - i.e. it trades away the RV1103's two genuine hardware advantages (the H.264/H.265 encoder and the ISP) to buy RAM. The report presents the encoder as a headline win and the CMA cut as free in the same document. Pick one, and say which.
- Nobody checked whether UART3 and UART4 can be routed simultaneously on the Pico Mini B's physical header. The Mini B exposes only ~17 GPIO and every pin is heavily muxed (Rev 1.5 Table 2-1 shows 3-6 alternate functions per pad); themrleon notes 'pin 54 supports 3.3v and can be PWM, UART or GPIO, but you must keep only one active at a time' and that functions must be enabled via luckfox-config. The claim '2 UARTs free' is a SoC-level fact that may not survive contact with this board's pinout. Verify against the Mini B pinout diagram before designing around two links.
- The determinism comparison is best-case-versus-worst-case and should be re-framed. NXP's 18.33 ns is a single ISR, code in TCM, no cache miss, no higher-priority interrupt pending, nothing else running. The Teensy 4.1 in this stack will simultaneously service USB, SysTick, at least two LPUART links and SPI. The honest comparison is worst-case to worst-case, and the M7's worst case is dominated by the longest interrupts-disabled window in the builder's own code - which the report's code guidance item 2 correctly identifies as the 43.4 us LPUART problem but never connects back to the latency claim. The stack's real determinism figure is 'the longest noInterrupts() region I ship', and that is measurable with the marker-pin method already proposed.
- INA219 shunt selection is not addressed for the actual measurement. At the +/-40 mV PGA setting with a nominal 0.1 ohm shunt, full scale is 400 mA; a Luckfox at ~1.2 W on 5 V draws ~240 mA and a Teensy 4.1 at 600 MHz draws ~100 mA, so the ranging works - but the report's own code guidance says to use the raw shunt register and a measured resistance without ever checking that the chosen PGA range and shunt value actually bracket the expected currents. Also unmentioned: the 0.5% accuracy spec plus a 4-wire-measured shunt still leaves the INA219's 10 uV shunt LSB as the resolution floor, which on 0.1 ohm is 100 uA - fine here, worth stating.
