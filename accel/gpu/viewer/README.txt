x11view (viewer/x11view.h, x11view.c) is a dependency-free X11 client library in C99 -- raw X11 protocol over POSIX sockets, no libX11/xcb, static-linkable -- used to show the FPGA's RGB565 frames in a window on the Pi's own desktop (SPEC 13.4): x11v_open(w,h,title) connects via $DISPLAY (":N[.S]" -> /tmp/.X11-unix/XN with Linux abstract-socket fallback, "host:N" / "tcp/host:N" / "[v6addr]:N" -> TCP 6000+N; static builds resolve host names from /etc/hosts only), authenticates with MIT-MAGIC-COOKIE-1 from $XAUTHORITY or ~/.Xauthority (entry matched by display number and FamilyLocal hostname / Internet address / wildcard; no entry = no auth; a refused cookie is retried once without, and the server's refusal reason is printed), parses the setup reply (resource-id base/mask, root, root visual and depth -- or the best TrueColor visual plus its own colormap if the root visual is not TrueColor --, pixmap formats -> bits-per-pixel and scanline pad for that depth, image byte order, maximum request length), enables BIG-REQUESTS when offered, creates the window with WM_NAME/_NET_WM_NAME, WM_CLASS, fixed-size WM_NORMAL_HINTS and WM_DELETE_WINDOW in WM_PROTOCOLS, maps it and creates a GC; x11v_put_rgb565() converts to the server's ZPixmap format (16/24/32 bpp, any TrueColor masks incl. 15- and 30-bit depths, either byte order; SSE2/NEON fast path for x8r8g8b8, 64K LUT otherwise) and uploads through MIT-SHM when the server provably sees our segment (pixmap round trip at start, else silent fallback) or through PutImage requests split into bands within the maximum request length (vertical strips if even one row is too long), sending only the rectangles that changed since the previous frame (adaptive, identical result) with at most one frame queued ahead of the server; x11v_poll() is non-blocking, drains events/replies/errors (X errors are printed with error code/name, request opcode/name, bad value and sequence and counted in x11v_get_info()), repaints Expose areas from the kept frame, and returns 1 once the window is closed (WM close button, Escape or q, window destroyed) or <0 when the connection is lost; all socket I/O is non-blocking with partial reads/writes handled, and x11v_set_title()/x11v_close() do what they say (extras: x11v_get_info, x11v_sync, x11v_read_rgb565 readback, x11v_fd, x11v_selftest; env X11V_NO_SHM, X11V_NO_BIGREQ, X11V_NO_DELTA, X11V_DEBUG). Build with `make` (static x86_64 + aarch64 build/<arch>/test_view and libx11view.a) and test with `make test` (offline self-test of every pixel format over all 65536 RGB565 values, 33-case matrix against the strict mock server tools/mock_xserver.py -- byte orders, 16/24/32 bpp, band and strip splitting, PseudoColor root, cookie auth incl. refusal and retry, TCP, MIT-SHM, fragmented I/O, forced partial writes, Expose, close/destroy/drop -- also under ASan/UBSan, and a live run); `test_view [seconds]` opens 1280x720, animates a moving gradient + scrolling colour bars + bouncing square + frame counter, prints fps each second and checks the window contents bit-exact via GetImage. Measured on this PC's WSLg XWayland (1280x720, 32 bpp, PutImage path since MIT-SHM is refused across WSLg's container boundary, while other jobs kept the CPU at ~100%): 180-270 fps with every pixel changing every frame and 800-840 fps when only small parts of the frame change; the aarch64 static binary passed the same live test under qemu-user (82 fps emulated).
